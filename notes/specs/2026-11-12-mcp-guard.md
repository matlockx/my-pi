# Plan: MCP guard with confirmation dialog

## Goal

Every call to the GitHub, Jira and jflow MCP servers passes one host-side guard. Destructive calls and
secrets or personal data in the arguments run only after the user clicks Allow in a native macOS dialog.
A direct `curl` to a real server achieves nothing, because only the guard holds the credential.

## Decisions (2026-11-12)

- **Approval channel**: the guard shows a native macOS Allow/Deny dialog itself (osascript). No answer
  within 110 s means deny. The omp MCP timeout goes to 120 s. A password relayed through the agent was
  rejected: it would land in the model context and provider logs, and the agent could replay it.
  Touch ID (LocalAuthentication helper) can replace the dialog later behind the same function.
- **jflow bypass**: `jflow mcp --http` requires `Authorization: Bearer $JFLOW_MCP_TOKEN` when that
  variable is set. The guard creates a random token at start and passes it only to its jflow child.
  nono port rules were rejected: they need a domain allowlist for all sandbox traffic.
- **Dialog policy: findings only.** A dialog appears for destructive tools, a secret or personal-data
  hit in the arguments, or a repository or Jira project outside the allowlist. Ordinary writes pass and
  are logged. A dialog on every write was rejected: review rounds and the unattended PR watcher would
  stall, and frequent dialogs train click-through.
- **Always allow**: when every finding of a request is a GitHub owner or Jira project outside the
  allowlist, the dialog offers a third button that adds those entries to
  `~/.config/mcpguard/allowlist.json` (per server, merged into the built-in list at every start).
  Destructive tools, default-branch writes, secrets and personal data never get the button. The file
  lives under `~/.config` because nono mounts it read-only: a sandboxed session cannot add entries.
- **jflow merge** is not a finding: jflow merges only after it has seen a coworker's approval.
- **aventine-kb** is out of scope for the MVP: remote, read-only, no credential held by the guard.

## Threat model

- MCP write tools run unprompted today (omp `tools.approvalMode` unset, default `yolo`).
- All servers listen on 127.0.0.1 without authentication; the sandboxed agent's `bash` or `eval` can
  call them with `curl`, so omp approvals are not a boundary.
- Prompt injection: Jira tickets, issue and PR comments and review threads are third-party text the
  agent reads.
- Exfiltration: comments, issue and PR bodies, Jira descriptions, Teams messages, new or forked
  repositories.
- Covered already: `secret-redactor` replaces secrets with placeholders before the agent sees them, and
  restoring a placeholder needs user approval. Personal data is not covered.

## Approach

One Node module, `mcp/guard/`, grown out of the GitHub token proxy (`mcp/github/proxy.mjs`). Per
server it starts the real server as a child on an internal port, injects the credential into every
forwarded request, inspects each JSON-RPC `tools/call` (batches included), and then forwards, blocks or
asks. A blocked call returns an MCP tool error (`isError: true`) naming the reason. Every decision is
appended to `~/.local/state/mcpguard.log`. Public ports stay 8082 (GitHub), 8084 (Jira) and 8765
(jflow); internal ports are 18082, 18084 and 18765.

## Status (2026-11-12)

All phases built and tested in the sandbox. Open on the host: the dialog from a `nohup` process
(Phase 1 manual check) and `my-pi-start restart` with the rebuilt jflow. Until jflow is rebuilt and
installed, the installed binary ignores `JFLOW_MCP_TOKEN` and port 18765 stays open to `curl`.

## Alternatives not taken

- Server flags only (`--exclude-tools`, `--enabled-tools`): no override when really wanted, no argument
  inspection.
- omp `tools.approval` prompts: bypassed by `curl` from `bash` or `eval`.
- nono port rules: need a domain allowlist for all sandbox traffic.
- Password relayed through the agent: lands in the model context.

## Risks

- Away from the desk: every finding is denied; the agent sees `denied by user or timeout`.
- Personal-data false positives (Jira e-mail fields, phone-like numbers): the audit log counts reasons;
  narrow the free-text field list.
- An Allow approves the call as shown: the dialog shows tool and the first 400 characters of the
  arguments.
- The jflow token is in the jflow child's environment: readable by host processes of the same user,
  not by the nono sandbox (`process_info_mode: allow_same_sandbox`).

## Done when

- `delete_file`, `jira_delete_issue` and any argument containing a secret run only after Allow.
- `curl` to 18082, 18084 or 18765 cannot write anything.
- Ordinary comments, issue updates and the jflow review flow run without a dialog.
- Every decision appears in `mcpguard.log`.
